# Phase 1 — Discover

Read client frontmatter, validate the contract (including security patches), build Gmail query strings, return per-client work tuples for Phase 2.

## Inputs (from orchestrator `commands/inbox-digest.md`)

- `run_id` — UUID v4 generated by orchestrator at run start; thread through every operational log line so a single run can be reconstructed
- `target` — one of: `<client-slug>` | `--all` | `--bootstrap <client-slug>`
- `since_iso` — optional ISO 8601 timestamp override (from `--since` flag)
- `vault_root` — `<your-vault-path>` (configurable per environment)

## Procedure

### 1.1 Resolve target list

A "client hub" is the per-client frontmatter+content note. Two supported layouts:
- **Folder layout:** `<vault_root>\context\clients\<slug>\index.md`
- **Flat-client layout:** `<vault_root>\context\clients\<slug>-client.md` (used when the vault already organizes clients with a sibling sub-folder + flat hub note; frontmatter contract identical)

Per-client thread notes always live in `<vault_root>\context\clients\<slug>\` (the sub-folder), regardless of layout. For flat-client layout, the sub-folder may already exist alongside the flat hub.

- If `target` is `--all`: Glob both shapes —
  - `<vault_root>\context\clients\*\index.md` (folder hubs; slug = parent folder name)
  - `<vault_root>\context\clients\*-client.md` (flat hubs; slug = filename minus `-client.md` suffix)
  Build a `slug → hub_path` map. If a slug has BOTH layouts, log a WARNING `"<slug>: both index.md and <slug>-client.md exist; using folder layout"` and prefer folder layout (deterministic tie-break).
- If `target` is `<client-slug>`: probe folder layout first, then flat-client layout. The FIRST match becomes `hub_path`. If neither exists → halt with bootstrap recommendation (see §1.2.a).
- If `target` is `--bootstrap`: hand off to `modules/bootstrap.md`; do NOT proceed with Phase 1 procedure.

### 1.2 Per-client validation (executed for each client in the list)

For each client, run validation steps **in this exact order**. A failure at any step **halts processing of THIS client only** (never halts the whole sweep). "Halt this client" and "Skip this client" mean the same thing in this module: stop processing this client, log the reason, move to the next client. Throughout the rest of this module, "halt this client" is the canonical phrase.

#### 1.2.a Hub note presence

A hub note for `<slug>` must exist in one of:
- `<vault_root>\context\clients\<slug>\index.md` (folder layout)
- `<vault_root>\context\clients\<slug>-client.md` (flat-client layout)

1. If NEITHER exists:
   - Output to user: `"Client '<slug>' has no hub note (looked for <slug>/index.md and <slug>-client.md). Run /inbox-digest <slug> --bootstrap to create one."`
   - SKIP this client.
2. Set `hub_path` to whichever was found. Set `hub_layout` to `"folder"` or `"flat-client"`. Both are carried forward through the rest of this phase and emitted in the §1.6 work tuple.

#### 1.2.b Read frontmatter

Read `hub_path` via `mcp__obsidian-brain__read_note` (preferred — vault-aware) OR direct file read. Extract YAML frontmatter into a structured object.

#### 1.2.c Slug validation (PATCH CIPHER-F2 — CRITICAL)

1. Validate frontmatter `slug` matches regex `^[a-z0-9][a-z0-9-]{0,40}$`. If not → halt this client with:
   `"slug '<value>' fails validation regex ^[a-z0-9][a-z0-9-]{0,40}$. Reject. Fix the frontmatter."`
2. Path containment check: compute `expected = Path(vault_root, "context/clients", slug).resolve()`. Verify `expected.starts_with(Path(vault_root, "context/clients").resolve())`. If not → halt this client with:
   `"slug '<value>' resolves outside vault clients dir; reject (path traversal protection)."`
3. Optional: also verify the on-disk hub identifier matches the frontmatter slug (catches drift):
   - `hub_layout == "folder"`: parent folder name must equal `slug`
   - `hub_layout == "flat-client"`: filename minus `-client.md` suffix must equal `slug`
   If mismatch, log a WARNING but proceed.

#### 1.2.d Required fields

Required keys (frontmatter must contain all):
- `client` (string, non-empty)
- `slug` (validated above)
- `gmail_accounts` (list, non-empty)
- AT LEAST ONE of `email_addresses` (list), `domains` (list), `aliases` (list) is non-empty

If any missing → halt this client with: `"Frontmatter missing required field '<name>'. Fix the frontmatter."`

#### 1.2.e gmail_label validation (PATCH CIPHER-F5 — HIGH)

If `gmail_label` is set: must match `^Clients/[A-Za-z0-9][A-Za-z0-9_-]*$`. If not → halt this client with:
`"gmail_label '<value>' must match Clients/* prefix (allowlist). Fix frontmatter or remove gmail_label."`

If `gmail_label` is null/missing: log a WARNING ("no gmail_label set; threads will not be auto-labeled") but proceed.

#### 1.2.f MCP auth verification (T0 sanity check)

Call `email-backend.verify_auth(expected_account=<frontmatter.gmail_accounts[0]>)`.
- If `ok: false`: halt this client with:
  `"MCP is auth'd to '<actual>', but '<slug>' expects '<expected>'. Switch MCP auth before continuing."`
- If `ok: true` AND `actual` is non-empty: definitive auth match — proceed.
- If `ok: true` AND `actual` is null/empty: NON-AUTHORITATIVE (no threads in last 7 days, MCP reachable but account identity unverified). Log a WARNING `"auth verify non-authoritative for <slug>: MCP reachable but no recent threads to confirm account"` and proceed. Phase 2 will catch any actual account mismatch on its first real fetch.

### 1.3 Compute scan window

For each validated client:
- If orchestrator passed `--since YYYY-MM-DD`: `window_start = parse_iso(since_arg)`
- Else if frontmatter `last_scan` is non-null: `window_start = parse_iso(last_scan)`
- Else (first run for this client): `window_start = now_utc() - 30.days` — sensible default for first-time clients to populate inbox without ingesting years of history

`window_end = now_utc()`

### 1.4 Build Gmail query

Construct an OR-joined query covering all match channels in frontmatter. Match logic = `match_strategy: any` (OR-logic). Query template:

```
( from:(<email1> OR <email2> OR @<domain1> OR @<domain2>)
OR ( from:(<relay1> OR <relay2>) AND ( subject:"<alias1>" OR <alias1> OR subject:"<alias2>" OR <alias2> ) )
OR ( from:me AND ( subject:"<alias1>" OR <alias1> OR subject:"<alias2>" OR <alias2> ) )
)
after:YYYY/MM/DD
```

Notes:
- Gmail's search supports `AND`, `OR`, parens for grouping.
- Multi-word aliases must be quoted: `subject:"<example-client>"`.
- `from:me` matches the authenticated user's address (captures self-notes that mention an alias).
- Format `after:` as `YYYY/MM/DD` from `window_start` (Gmail's native format).
- If a frontmatter list is empty, OMIT that branch — don't generate `from:()` (empty parens are a Gmail syntax error).
- If ALL match channels are empty (impossible if 1.2.d passed, but defensive): skip this client with `"no match rules configured"` log entry.

### 1.5 Backfill safety gate (PATCH PHANTOM-F6)

If `(window_end - window_start) > 30 days`:

1. Call `email-backend.search_threads(query, after_iso=window_start_iso, page_size=1)` to get an estimate. The `after:` clause is already in `query`; passing `after_iso` keeps the call signature aligned with the adapter contract. The `{capped}` flag in the response indicates >500 results — treat as "definitely above threshold" without further estimation.
2. If estimated total > frontmatter `backfill_confirm_threshold` (default 100), present `AskUserQuestion`:
   - **Proceed** (Recommended for routine catch-up): scan everything in window
   - **Narrow**: prompt for a tighter `--since` date, recompute window
   - **Cancel**: skip this client this run; don't update `last_scan`
3. Honor the response. If non-interactive context (cron run): default to **Cancel** + log warning. Cron should never block on user input.

### 1.6 Output

Return list of work tuples for Phase 2:

```yaml
- client_slug: <example-client>
  client_display: "<example-client> — <example-client>"
  hub_path: "<vault_root>\\context\\clients\\<example-client>-client.md"
  hub_layout: "flat-client"          # one of "folder" | "flat-client"
  query_string: "(from:(...)...) after:2026/05/01"
  window_start_iso: "2026-05-01T00:00:00Z"
  window_end_iso: "2026-05-08T19:00:00Z"
  priority: high
  match_strategy: any
  gmail_label: "Clients/ExampleClient"   # validated; null if not set
  expected_account: "<your-email>"
  client_dir: "<vault_root>\\context\\clients\\<example-client>"
```

`client_dir` is always the sub-folder (used by Phase 2 for thread notes). For `hub_layout == "flat-client"`, Phase 2 creates `client_dir` lazily on first write if absent.

Phase 2 consumes this list and uses `hub_path` for the `last_scan` frontmatter atomic update — never assume `<client_dir>/index.md`.

## Failure modes summary

| Condition | Action |
|---|---|
| Missing hub note (neither `<slug>/index.md` nor `<slug>-client.md`) | Skip client, recommend `--bootstrap` |
| Slug regex/path-traversal fail | Halt this client, log security warning |
| Required frontmatter field missing | Skip this client, name the field |
| `gmail_label` allowlist fail | Halt this client, request fix |
| MCP auth mismatch | Halt this client (do NOT touch other clients) |
| Backfill > threshold (interactive) | AskUserQuestion gate |
| Backfill > threshold (cron) | Cancel this client, log warning |
| All match channels empty | Skip this client, log "no match rules configured" |
